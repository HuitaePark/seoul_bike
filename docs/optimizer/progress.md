## 최신 main의 상태

Spring Boot 백엔드는 backend/로 이동했고 Vue 공통 뼈대는 frontend/에 있다.
로그인·회원가입·계정 관리·작업 API·SSE·승인·ai.tasks 발행·ai.events 소비가 구현됐다.
agent 자리는 설정으로 켜는 가짜 에이전트가 대신하며 ai.events 소비의 retry/DLQ가 구현됐다.
현장 보고 생성, 내부 서비스 토큰, 현장 보고 조회·제약 추가·감사 로그가 구현됐다.
대여소·계획·성과 API, 나머지 내부 API와 backend의 solve.* 연결은 아직 계약 단계다.
경로 변경은 backend가 정한 requiredApprovers 순서로 승인한다. MINOR는 기사, MAJOR는 관리자 → 기사다.
변경 등급·승인 순서 검사와 Harness의 공통 계약 대응도 반영했다.
기존 최적화 코어와 이번 OSRM 변경은 개인 브랜치에 있으며 main에는 아직 없다.

## 협의·연결이 필요한 항목

재경로·p95·메모리 캐시 비교와 worker 실행 로그 보강을 완료했다.
이번 재경로 측정은 행렬 외 엔진 시간이 대부분이므로 모델 구성·탐색·결과 추출의 상세 프로파일링이 다음 성능 작업이다.
명세 기반 가짜 API의 지도·계획 검토 화면도 단독 개발할 수 있으며, 지도 서비스 선택과 실제 데이터 연결은 담당자와 확인한다.
아래 운영 통합 항목은 아직 남아 있다.

1. **운영 설정·backend 연결:** [공통 대응 명세](../specs/optimizer.md)를 기준으로
   권역·스냅샷의 차고지·기준 시각을 자동 공급하는 경로를 담당자와 확인한다.
   로컬 worker는 저장 결과를 재사용하지만 발행 직후 장애에서는 동일 결과 eventId가 재전달될 수 있다.
   backend 결과 소비 중복 제거·운영 저장소·보존·재시도/DLQ 정책을 확정하고 실제 흐름에 연결한다.
2. **역할 6과 권역·정책 확정:** 도로 파일 범위와 버전, 운영 상한, 우선순위,
   근무시간·작업시간을 확정한다. 그 입력으로 실제 도로의 200곳·5대 성능을 측정한다.
   S05 참조 시드는 준비했으나 중심 좌표는 대여소 좌표 평균이다. 실제 운영 차고지와 관측 시각·재고는 별도로 받아야 한다.
3. **준비된 Vue 공통 뼈대 사용:** frontend/src/features/plan-map/의 지도·계획 검토 설계를 진행할 수 있다.
   공유 API 클라이언트·생성 타입·useTaskStream을 사용하고, 실제 업무 API가 준비되기 전에는 명세 기반 가짜 API를 쓴다.
4. **서버 운영 담당과 통합:** 지도 전처리 메모리·디스크 예산과 배포 절차를 확인한 뒤
   운영 Compose에 연결하고 전체 실행·재경로 10초를 검증한다.
