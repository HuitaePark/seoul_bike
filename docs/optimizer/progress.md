## 최신 main의 상태

Spring Boot 백엔드는 backend/로 이동했고 Vue 공통 뼈대는 frontend/에 있다.
로그인·회원가입·계정 관리·작업 API·SSE·승인·ai.tasks 발행·ai.events 소비가 구현됐다.
에이전트 그래프와 공통 승인 카드가 main에 병합됐고, 로컬 예시는 가짜 에이전트를 끄고 실제 agent 컨테이너를 사용한다.
관리자 대시보드·기사 앱·성과 리포트 더미 화면과 역할별 첫 화면이 추가됐다. Harness 현장 보고 fixture 수정으로 기존 CI 테스트 제외도 해제됐다.
ai.events 소비의 retry/DLQ와 로그인 실패·승인 대기 가입 수 제한도 반영됐다.
현장 보고 생성, 내부 서비스 토큰, 현장 보고 조회·제약 추가·감사 로그가 구현됐다.
PR #32로 backend의 SolveGateway·SolveResultConsumer·요청 상태 저장과 solve 토픽이 추가됐다.
worker는 운영 Compose에 편입됐고 실제 메시지 입력 공급·전체 업무 통합이 남아 있다. 계획 조회·활성화·경로 적용과 기사 오늘 경로 조회는 구현됐고, 대여소·성과 API와 나머지 내부 API는 아직 계약 단계다.
비활성화한 계정은 기존 JWT도 다음 요청부터 401이며, 이미 열린 SSE는 즉시 종료하지 않는다.
backend 포트는 서버 로컬로 제한했고 화면 nginx에는 지도 외부 자원을 고려한 보안 헤더가 반영됐다.
경로 변경은 backend가 정한 requiredApprovers 순서로 승인한다. MINOR는 기사, MAJOR는 관리자 → 기사다.
변경 등급·승인 순서 검사와 Harness의 공통 계약 대응도 반영했다.
최적화 코어·OSRM·Kafka 실행기와 지도 검토는 같은 저장소에서 제공한다. 운영 worker의 이동 시간은 하버사인 추정이며 OSRM·실제 수요 입력·전체 업무 통합은 후속이다.

최적화 코어는 업무 DB에 직접 접근하거나 LLM을 호출하지 않는다. 기존 CLI는 가상 대여소·예측 데모다.
별도 contract.solve_request()는 공통 메시지의 계산된 neededBikes를 받으며,
메시지의 depot·asOf와 명시적 이동 공급자를 사용한다. worker는 requestId별 runtime 파일 없이 Kafka를 처리한다. backend 요청 생성·결과 소비 구현은 main에 있지만 실제 worker와 운영 통합 검증은 남아 있다.

  실제 6파티션 브로커에서 7개 UTF-8 키·출력 3토픽·키별 2건(총 42건)의 분배·헤더·순서를 확인했다.

- 운영 worker의 Compose 편입과 PR #46의 로컬 스모크 기록을 안내에 반영했다.
  아직 없는 실제 수요 입력 생성·OSRM·전체 업무 통합을 완료로 표시하지 않는다.

  운영 서버 변경이나 새 CI 잡은 추가하지 않았다.

## 시간별 예측 연결

- 데이터 담당의 junyeop-ortools 3b773e9 중 안 B 인터페이스를 검토해 현재 코어에 반영했다.
  날짜·1~5시간·모델 버전·실수 배열을 수용하고, 기본 1시간과 기존 9개 mock 시나리오 필요량을 유지한다.
- naive KST와 UTC/+09:00 입력을 같은 정시 창으로 정규화한다. 비정시·배열 길이·버전·수요 오류는 거부한다.
- 시간별 합계를 Decimal로 계산하고 최종 목표 하한 올림·상한 내림으로 정수 필요량을 만든다.
- data 모듈의 세 예측기 출력과 연결했다. 학습·시뮬레이터 정책·공개 API·Kafka payload는 변경하지 않는다.
  운영 worker는 여전히 계산된 neededBikes를 받는다. 모델 품질·실제 서버 입력 공급을 완료했다는 뜻은 아니다.
- 실제 Kafka 포함 최적화 323개·subtest 24개, 데이터·시뮬레이터 18개 통과.
  베이스라인 실제 호출과 LightGBM/Nowcast 캐시 클래스의 출력 연결을 확인했으며, 학습 품질은 측정하지 않았다.

## 협의·연결이 필요한 항목

참조 시드의 서울 17개 구역 확장과 N01 265곳 가상 작업량 측정을 완료했다([측정](benchmarks/n01-265.md)).
최종 PR 제출 전 확인과 이후 운영 연결 순서는 [PR 준비 상태](pr-readiness.md)에 정리했다.
가짜 구역·대여소의 화면 교체는 각 담당자의 가짜 데이터 이전과 대여소 API 준비 후 함께 진행한다.

재경로·p95·메모리 캐시 비교와 worker 실행 로그 보강을 완료했다.
모델 구성·탐색·결과 추출의 상세 측정에서 Python 평가 콜백을 병목으로 확인해 native 행렬/벡터로 변경했다.
단계별 원시 표본·전후 입력/계획 해시와 재현 절차는 [성능 기록](benchmarks/native-transit.md)에 있다.
다음 성능 검증은 실제 OSRM 도로·운영 서버와 backend를 연결한 전체 흐름이며 필요한 권역·도로 자료는 아래와 같다.
계획 검토 화면에 MapLibre·OpenFreeMap 지도·마커·방문 순서를 연결했다. 실제 도로선·업무 데이터 연결은 남아 있다.
아래 운영 통합 항목은 아직 남아 있다.
백엔드 제안에 동의해 depot{lat,lon}·시간대 있는 asOf·오류/미처리 사유 enum의 계약 PR은 역할 4가 맡고,
역할 5는 solve.requests.retry → .dlq와 PR #34의 메시지 설정·실패 필드·대문자 사유 대응을 구현했다.
backend가 요청 retry/DLQ 토픽도 app.kafka.partitions(기본 6)로 생성한다. backend healthy 이후 worker 시작·상태 볼륨·헬스체크는 PR #46에 반영됐다. main에 병합된 데이터 PR #10은 forecast/에 datetime 예측기를 제공하며, or-tools의 날짜·시간별 예측 연결을 hyunmoo에서 구현했다. 운영 입력 구성과 예측 DB 연결은 후속이다.

1. **운영 설정·backend 연결:** [공통 대응 명세](../specs/optimizer.md)를 기준으로
   권역·스냅샷의 차고지·기준 시각을 자동 공급하는 경로를 담당자와 확인한다.
   로컬 worker는 저장 결과를 재사용하지만 발행 직후 장애에서는 동일 결과 eventId가 재전달될 수 있다.
   backend 결과 소비 중복 제거와 시간 초과 정책을 확인하고 운영 저장소·토픽 보존·DLQ 관제/재처리를 실제 흐름에 연결한다.
2. **운영 입력 확인:** 기본 3시간·Station.docks·운행 설정·구역 참조 트럭 기본값과 로컬 300곳 검사를 반영했다.
   도로 파일 범위/버전·실제 차고지·운영 상한·우선순위는 역할 4·6과 확인한다.
   실제 도로의 265/300곳·5대 성능과 전체 10초는 별도 측정한다.
   서울 17구역 참조 시드는 준비했으나 중심 좌표는 대여소 좌표 평균이다. 실제 운영 차고지와 관측 시각·재고는 별도로 받아야 한다.
3. **계획 검토 실제 연결:** frontend/src/features/plan-map/에 실제 조회·공개 시연을 분리해 구현했다.
   공유 API 클라이언트·생성 타입·useTaskStream을 사용한다. backend 계획 조회·활성화·대여소 API는 구현됐으며
   실제 입력 공급을 연결한 뒤 새 후보 승인 흐름을 실제 서버와 통합 검증한다. [화면 명세](../specs/plan-review.md)에 현재 제공되지 않는 상세 항목을 기록했다.
   지도 점선은 방문 순서로 표시한다. 실제 도로선은 OSRM Route 조회와 공개 응답을 역할 4와 협의해 추가한다.
4. **서버 운영 담당과 통합:** 지도 전처리 메모리·디스크 예산과 배포 절차를 확인한 뒤
   OSRM을 운영 Compose에 연결하고 전체 실행·재경로 10초를 검증한다.
