## 재경로 성능 측정·worker 실행 추적

- 기준은 개인 브랜치 61e8101이다. benchmark·worker와 검증·안내를 확장했으며 계산 모델,

- benchmark에 가상 REPLAN 스냅샷, nearest-rank p95, 메모리 캐시 none/cold/warm 비교,
  행렬·실제 공급자·나머지 엔진 시간과 입력 해시를 추가했다. 기존 명령의 기본 PLAN 출력도 유지했다.
- 재경로는 초기 계획의 차량별 첫 작업을 마친 뒤 대기하는 공통 시각을 만들고 현재 위치·적재량·재고와
  남은 근무시간을 갱신한다. 완료 거점은 제외하고 남은 한 곳은 진입 불가로 처리한다.
  warm의 사전 호출과 스냅샷 생성은 표본에서 제외하고 별도 시간으로 기록한다.
- 단위·회귀 검사 **201개·24개 subtest 통과**, 실제 Kafka를 포함한 전체 실행은 **202개·24개 subtest 통과**.
  기존 OR-Tools SWIG 경고 3건이 있다.
- 신규 검사는 p95 계산·실제 공급자 호출 횟수·warm 준비 제외·캐시별 계획 동일성,
  재경로의 완료 거점 제외·진입 불가·재고와 적재량 보존을 확인한다.
- worker의 JSON 로그는 UTC 시각, 입력·결과 ID, 처리·계산 시간과 캐시 증분, 실패 단계·코드를 남긴다.
  이번 computeMs와 저장 결과의 과거 resultSolveMs를 구분한다. 중복 요청은 재계산하지 않는다.
- lookup·context·compute·publish·mark_published·commit 실패에서 offset을 commit하지 않고 예외를
  유지하며, 실패 단계는 남기되 임의 예외 본문·깨진 입력 본문은 기록하지 않는 검사를 통과했다.
  계산 FAILED도 결과가 발행·commit되면 solve.completed로 기록하는 것을 확인했다.
- 별도 Redpanda 브로커에서 실제 두 프로세스의 JSON 로그와 재시작·중복 제거·상관관계·공통 결과 스키마,
  결과 2건·입력 5건의 offset 완료를 검증했다. 전용 컨테이너·네트워크·테스트 볼륨을 정리했다.
- 200곳·5대의 조건별 20회 원시 측정값과 범위는 [측정 기록](benchmarks/README.md)에 보관한다.
  초기 계획 p95는 none/cold/warm에서 각각 0.102/0.097/0.084초,
  재경로는 5.942/5.987/6.370초였다. 각 시나리오의 입력·계획 해시는 캐시 조건과 반복 실행에서 동일했다.
  REPLAN의 첫 compare 실행은 측정 스크립트의 300초 상한에서 중단되어 제외했고 조건별로 다시 측정했다.
  준비된 캐시는 공급자 호출을 없앴지만 이번 재경로의 전체 시간 개선은 확인하지 못했다.

실제 OSRM 도로망과 운영 backend·Kafka 대기·LLM을 포함한 전체 응답시간은 이 로컬 측정에 포함되지 않는다.
하버사인 기반 결과로 운영 재경로 p95 10초 완료를 판정하지 않는다. MCP·backend·frontend는 이번 변경에서 다시 실행하지 않았다.
