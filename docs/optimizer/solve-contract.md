# solve 요청·결과 명세 초안

상태: **Python 코어 입력·출력 설명과 검토 의견**. Kafka 실행기는 아직 구현하지 않았다.
main `aebf8a6`에 추가된 [공통 API·Kafka 명세](../specs/README.md)가 외부 인터페이스의 원본이다.
아래 snake_case 예시는 코어 모델 설명용이다. 실제 전송 필드는 공통 AsyncAPI의 camelCase를 따른다.
공통 초안과 코어의 차이·추가 결정은 [연결 검토](contract-review.md)에 정리했다.

## 호출 흐름

최신 README·ROLES와 03a/03b 구성도 기준으로 백엔드가 `solve.requests`를 발행하고
optimizer가 계산 결과를 `solve.results`로 돌려준다. Agent는 MCP를 통해 요청한다.
optimizer는 LLM을 호출하거나 업무 DB에 접근하지 않는다.

## 요청에 필요한 정보

| 묶음 | 필드/의미 |
| --- | --- |
| 상관관계 | `request_id`, `schema_version`, `trace_id`, `shift_id`, `base_plan_version` |
| 기준 시각 | `as_of`: 시간대가 있는 ISO 8601 시각. 모든 차량의 남은 시간과 ETA가 이 시각 기준 |
| 재고 스냅샷 | 대여소 ID·좌표·거치대 수·현재 재고·운영 상한, 관측 시각 |
| 필요량 | 대여소별 `delta` (+회수/-보충), 선택적 우선순위 점수와 산출 근거 |
| 차량 상태 | ID·용량·현재 적재량·현재 위치·`available_time_s` |
| 제외 조건 | 완료한 거점, 진입 불가 거점, 관리자 제외 조건과 유효 기간 |
| 운영 설정 | 작업 시간, 유형 가중치, 해 개수 제한, 차고지 위치, 이동 행렬/도로망 버전 |

코어의 ID는 현재 정수이며 공통 초안의 외부 ID는 `ST-1023`과 같은 문자열이다.
연동 어댑터가 원본 ID를 복원할 수 있는 매핑을 담당한다. 임의로 정수로 잘라 변환하지 않는다.

요청의 재고는 거치대 수보다 많을 수 있다. 트럭은 `0 <= load <= capacity`여야 하고,
모르는 대여소·중복 ID·0 필요량·현재 재고를 넘는 회수량·잘못된 행렬은 입력 오류로 처리한다.
남은 근무 시간은 백엔드가 `shift_end - as_of`로 계산하며 음수 값은 거부한다.

### 가상 재경로 입력 예

아래는 연동 문서용 예시이며, 이를 읽는 Kafka 소비자가 구현됐다는 뜻은 아니다.

```json
{
  "schema_version": "0.1-draft",
  "request_id": "region-a:2026-10-20:am:3:1",
  "trace_id": "demo-trace-001",
  "shift_id": "region-a:2026-10-20:am",
  "base_plan_version": 3,
  "as_of": "2026-10-20T08:00:00+09:00",
  "depot": [37.0, 127.0],
  "stations": [
    {"id": 1, "name": "회수 완료", "lat": 37.01, "lon": 127.0, "capacity": 10, "bikes": 6},
    {"id": 2, "name": "보충 대상", "lat": 37.02, "lon": 127.0, "capacity": 10, "bikes": 0}
  ],
  "imbalances": [{"station_id": 1, "delta": 4}, {"station_id": 2, "delta": -4}],
  "trucks": [{"id": 0, "capacity": 15, "load": 4, "position": [37.01, 127.0], "available_time_s": 3600}],
  "completed_station_ids": [1],
  "blocked_station_ids": []
}
```

완료 거점 1은 다시 방문하지 않는다. 트럭은 실제 위치에서 4대를 싣고 출발하며
거점 2에 보충한 뒤 차고지로 복귀한다. 완료 대수를 현재 적재량에 다시 더하지 않는다.

## 결과

요청의 상관관계 필드와 `base_plan_version`을 그대로 반환한다. `plan`은 코어의
`Plan`을 직렬화한 후보 경로이며, 활성 계획을 직접 변경하지 않는다.

- `routes`: 트럭별 `start_load`, 순서가 있는 `stops`, `distance_m`, `duration_s`.
- `stops`: 대여소 ID, `action`, `bikes`, `load_after`, `arrival_s`, `departure_s`.
- 상대 초는 백엔드가 `as_of`에 더해 절대 ETA로 표시한다.
- `unserved`: 남은 필요량. 완료 거점은 포함하지 않는다.
- `unserved_reasons`: 코드 설명은 [개발 안내](README.md)의 표를 따른다.
- `status`: `complete`, `partial`, `no_solution`. `complete`는 입력의 처리 대상을
  모두 방문했다는 뜻이며, 실제 수요를 모두 충족하거나 미래 위험이 없다는 뜻은 아니다.
- 실행기는 별도로 `elapsed_ms`, solver 버전·설정, 행렬 출처·버전, 오류 정보를 기록한다.

코어 호출은 `ValueError`로 잘못된 입력을 알린다. 실행기에서는 이를 재시도할 수 없는
입력 오류로 직렬화하고, OSRM·브로커 연결 장애 같은 일시 오류와 분리해야 한다.

## 합의가 필요한 결정

| 결정 | 제안/검토 사항 |
| --- | --- |
| 필요량 계산 위치 | 코어는 필요량을 입력으로 받음. `compute_imbalances` 호출 책임과 예측의 시간 버킷은 4·6번과 확정 |
| 우선순위 단위 | 명시 점수 × 미터 환산 비용. 수요 강도·임박도 정규화와 2:1 기본 가중치 검토 |
| 중복 처리 | 요청 ID만으로 재시작 이후 중복을 막을 수 없음. 백엔드의 영속 요청/결과 기록과 중복 반영 방지 필요 |
| 오래된 결과 | 기준 버전이 현재 계획과 다르면 백엔드가 적용하지 않고 재요청 여부 판단 |
| 시간 예산 | 초안 60초와 재경로 전체 10초의 예산을 구분. 큐 대기·행렬 조회·계산·설명 시간 배분 |
| 재시도/DLQ | 4번의 공통 명세에 맞춤. 입력 오류를 반복 재시도하지 않음 |
| 재경로 범위 | 이동 중 다음 정류장 고정 여부, 트럭 간 배정 변경 허용, 중지 대여소 사전 회수 정책 |
| 미처리·부분 처리 | 현재 전량/미처리 모델 유지 여부. 큰 필요량을 여러 방문으로 나누는 정책 검토 |
| 도달 불가 | OSRM의 `null` 구간을 제외/오류/명시적 추정 중 어떻게 다룰지 확정. 0초로 변환 금지 |

공통 AsyncAPI 스키마를 기준으로 위 결정을 검토하고, 합의 후 연동 어댑터와 요청·결과 fixture를 추가한다.
계획 승인·변경 등급 분류·감사 로그·계획 버전 증가는 백엔드/에이전트 흐름에서 담당한다.
