# 역할 5 — PR 준비와 남은 통합 작업 (2026-10-21)

현재 작업 브랜치는 `hyunmoo`다. 최신 반영 기준은 main `df9ea43`(대여소 API #83, 화면 정리 #84, 데이터 검사 #85),
병합 커밋 `2936c16`이다. 이 작업에서는 PR 없이 브랜치에 커밋·push한다.

## 확인한 PR과 반영 범위

- 열린 [PR #75](https://github.com/HuitaePark/skala_seoul_bike/pull/75)는 근거 패널의 제목/절 분리 수정이다.
  확인 시 저장소 CI 9개와 CodeRabbit 검사가 성공했고 사람 리뷰 대기였다. 역할 5 코드와 겹치지 않아 가져오거나 수정하지 않았다.
- [PR #83](https://github.com/HuitaePark/skala_seoul_bike/pull/83)의 대여소 현황·위험·상세·예측 API는 main에 병합됐다.
  공개 API 0.13.0·내부 API 0.8.0-draft, Kafka 0.5.1-draft·payload schemaVersion 1 기준이다.
- 운영 중이고 관측이 있는 대여소만 공개 현황에 나온다. 관측 없는 구역은 200 빈 목록이고, 예측이 없으면
  forecastBikes는 null이다. 이 응답을 오류/시연 데이터/0으로 바꾸지 않으며 계획이 없어도 목록·상세를 표시한다.
  실제 수집·예측 적재와 승인 왕복의 운영 검증은 별도다.

## 현재 브랜치에 완료한 독립 변경

- 지도 최초 범위 맞춤과 늦은 load 재확대 수정, 예측 구간 1~5시간 제한.
- Java 호환 Kafka 파티션 선택과 6파티션·3토픽·42건 검증.
- 시간별 실수 예측·버전·KST 날짜 연결과 최종 정수 필요량 변환.
- 서울 17구역·2,716곳 원본 검증, 대여소번호↔ST-ID 대응/해시 검사.
- 합의 16·17·19 적용: 기본 예측 3시간, Station.docks, 거리 ×1.3·시속 20km.
  데이터/시뮬레이터 소비처를 함께 갱신했다. 차량 Truck.capacity는 적재 용량이며 wire 계약을 바꾸지 않았다.
- 합의 20 적용: 구역 참조 benchmark는 trucks_min을 기본값으로 쓰고 명시 입력을 우선한다.
  가상 --stations 모드는 기본 5대를 유지한다. 운영 fleet은 생산자가 실제 가용 차량으로 구성해야 한다.
- [확정 운행 설정의 N01·300곳 측정](benchmarks/agreed-policy-300.md). 실제 좌표/가상 상태와 가상 300곳을 구분하며
  로컬 엔진·메모리 범위만 검증한다. 실제 도로/업무 전체 재경로 10초 통과를 뜻하지 않는다.
- backend의 +09:00 입력은 RFC 3339로 받는다. 현재 AsyncAPI에서 optimizer 결과의 UTC 표기는 허용하며 기존 결과 형식을 유지한다.

## 최종 PR 제출 직전

1. 제출 시점의 origin/main을 확인하고, 추가 변경이 있으면 병합·영향 범위 검사를 한다.
2. 개인 브랜치 전체 변경과 검증 결과·실제 도로/데이터 미통합 범위를 PR 설명에 적는다.
3. 사용자 요청 시 PR을 만든다. 시간별 예측/명칭 소비처는 역할 6, 생산자 neededBikes/priority와 API 연결은 역할 4가 검토한다.
   공통 계약을 새로 바꾸는 후속은 ROLES의 계약 명세 승인 규칙을 따른다.
4. PR 생성 후 전체 GitHub CI와 리뷰를 확인한다. 현재 CI는 PR/main push에서 실행하며 hyunmoo push로 실행되지 않는다.
   로컬 backend 검사는 Java 25가 필요하다. 실행한 범위는 [검증 기록](validation.md)에 남긴다.

위 독립 변경의 PR 전에 아래 운영 통합을 전부 끝낼 필요는 없다. 운영 통합을 포함한 최종 완료는 별도 검증해야 한다.
