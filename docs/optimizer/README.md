# 최적화 코어 개발 안내

역할 5의 독립 작업 범위다. 코드 위치는 기존 `or-tools/`를 유지한다.
공통 모듈 이전, Kafka 연결, 운영 배포 구성은 이 변경에 포함하지 않는다.
독립 실행용 [OSRM 개발 환경](../../infra/optimizer/README.md)은 별도로 제공한다.

## 실행

저장소 루트에서 Python 3.12로 환경을 만든다. CI도 Python 3.12를 사용한다.
Python 3.14가 기본인 macOS에서는 `uv venv --python 3.12 .venv`로 대신 만들 수 있다.
uv 환경에서는 아래 pip 설치 대신 `uv pip install --python .venv/bin/python -r requirements.txt -r or-tools/requirements-dev.txt`를 사용한다.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt -r or-tools/requirements-dev.txt
cd or-tools
../.venv/bin/python -m pytest -q
../.venv/bin/python -m rebalancing --hour 8 --trucks 3
../.venv/bin/python -m rebalancing --hour 18 --trucks 2 --start-load 7 --json
```

`requirements.txt`는 루트에 있고, Python 패키지는 `or-tools/`에 있다.
명령의 실행 위치를 위와 같이 나눈다. 실제 API 키와 서버 설정은 필요하지 않다.

## 현재 구현

| 항목 | 동작 |
| --- | --- |
| 트럭 | 기본 용량 15대, 출발 적재량 0대. 관측된 적재량은 `load`로 반드시 전달 |
| 현재 위치 | `Truck.position`에서 출발. 생략하면 차고지 |
| 시간 | `available_time_s` 안에 이동, 작업, 차고지 복귀까지 완료. 기본 3시간이며 저녁 근무조 등은 별도 지정 |
| 작업 시간 | 정류장당 180초 + 자전거당 30초. `PlanningOptions`로 변경 |
| 재경로 | 현재 위치·적재량을 전달하고 `completed_station_ids`, `blocked_station_ids`로 대상 조정 |
| 배정 고정 | Truck.fixed_station_ids로 처리 차량 제한. 방문 순서·방문 필수는 지정하지 않음 |
| 완료/진입 불가 | 완료된 거점은 계산·미처리에서 제외. 진입 불가 거점은 `blocked` 사유로 미처리 |
| 대여소 운영 상한 | `Station.operating_limit`, 생략하면 거치대 수. 현재 재고와 목표 재고를 거치대 수로 잘라내지 않음 |
| 우선순위 | `Imbalance.priority`가 있으면 사용. 없으면 필요 대수 × 유형 가중치 (부족 2, 과적재 1) |
| 탐색 | `PATH_CHEAPEST_ARC` + `GREEDY_DESCENT`, 기본 `solution_limit=50`. 지역 최적에 도달해도 종료 |
| 비교 기준 | 탐욕 방식도 같은 출발 적재량, 차량별 용량·근무시간, 거리·시간 행렬, 작업 시간을 사용 |
| 결과 | 도착·작업 종료 상대 시각, 적재량, 복귀 포함 운행 시간, 미처리 사유, 전체 처리 상태 |

부족/과적재 가중치 2:1은 **검증 전의 실험 기본값**이다. 수요 강도·임박도를
반영한 정식 우선순위는 데이터 담당과 계약을 맞춰 전달해야 한다. 현재 예측기는
구간 합계만 돌려주므로 시간별 재고 궤적, 빈 시각, 예측 구간 중간의 안전은 계산하지 않는다.
현재 재경로는 완료/진입 불가 제외와 새 위치·적재량 반영까지이며, 이동 중인
다음 정류장의 방문 순서 고정은 후속 작업이다. 차량 배정 제한은 두 정책에 반영했다.

기본 출발 적재량은 두 정책 모두 0대다. 차고지에 충분한 재고가 있다는 이유로
솔버가 임의로 자전거를 만들어 싣지 않는다. 차고지 재적재·부분 처리는 아직 지원하지 않는다.

## 이동 시간 공급자

`TravelTime.matrix(points) -> TravelMatrix`를 주입한다. 계산 엔진은 HTTP·Kafka·DB를 모른다.

- 행/열은 요청받은 `points` 순서를 그대로 따른다. 좌표는 `(위도, 경도)`다.
- `distances_m`: 정수 미터, `durations_s`: 정수 초. 비대칭 행렬을 허용한다.
- `None`, 음수, 잘못된 크기는 거부한다. 도달 불가 구간을 0으로 바꾸면 안 된다.
- 기본 공급자는 하버사인 거리와 시속 30km로 만든 **개발용 추정치**다. 실제 도로 경로나 실시간 교통이 아니다.
- `OsrmTravelTime`은 OSRM Table API의 도로 거리·시간을 연결한다. 초·미터는 올림하여 정수로 만들고,
  중복 좌표를 한 번만 조회한 뒤 원래 순서로 복원한다. 기본 100개 좌표 한도를 넘으면 두 축을 분할한다.
- `CachedTravelTime`은 메모리 LRU와 선택적 디스크 캐시를 제공한다. 두 저장소 모두 최대 16개 행렬,
  TTL 1시간이 기본이다. 디렉터리는 캐시 전용으로 사용한다. 위치나 순서가 바뀌면 전체 행렬을 다시 만든다.
- 캐시 키는 좌표 순서·서버·프로필·데이터 버전·스냅 반경을 포함한다. 디스크 캐시 사용 시
  `--osrm-data-version`을 명시해야 한다. 그 버전은 PBF·Lua 프로필·엔진·전처리 설정이 바뀔 때 갱신한다.
  서버를 같은 URL에서 바꾸고 버전을 유지하면 캐시가 만료될 때까지 이전 결과를 읽을 수 있다.
- 깨지거나 만료된 캐시는 다시 계산한다. 디스크 기록 실패는 경고를 남기고 유효한 계산 결과를 반환한다.
  공급자 오류는 캐시에 넣지 않는다. 워커별 순차 호출을 전제로 하며 동시 요청을 합치는 잠금은 없다.
- HTTP 타임아웃은 요청당 기본 3초, 행렬 예산은 8초다. 블록 요청 전후에 예산을 확인하고
  남은 시간을 다음 요청의 타임아웃에 반영한다. 소켓 타임아웃은 개별 I/O 제한이므로 전체 흐름의 엄격한
  8초/10초 상한을 보장하지 않는다. 자동 재시도는 없으며 `TravelTimeError.code/retryable`로 상위에 전달한다.
- 도달 불가 셀 하나라도 있으면 전체 행렬을 거부한다. 일부 거점을 건너뛰는 복구 정책은 아직 구현하지 않았다.

실행 예시와 지도 파일 준비는 [독립 개발 환경](../../infra/optimizer/README.md)을 따른다.
공통 메시지는 [AsyncAPI](../specs/asyncapi.yaml)를 따른다. 변환·계산 함수와 실행 설정은
[역할 5 명세](../specs/optimizer.md)에 있다. Kafka 전송·중복 제거 실행기는 후속 작업이다.

## 미처리 사유

| 코드 | 확인된 사실 |
| --- | --- |
| `blocked` | 입력에서 트럭 진입 불가로 지정 |
| `no_trucks` | 사용 가능한 차량 목록이 없음 |
| `capacity_exceeded` | 한 번에 처리할 필요량이 모든 차량의 용량보다 큼 |
| `no_solution` | 해당 탐색에서 해를 얻지 못함. 불가능하다고 증명했다는 뜻은 아님 |
| `not_selected` | 시간·적재량·비용을 고려한 결과 선택되지 않음. 개별 원인은 확정하지 않음 |

노드가 빠졌다는 사실만으로 "시간 부족" 또는 "적재량 부족"이라고 단정하지 않는다.
사유를 더 세분화하려면 추가 진단과 별도 검증이 필요하다. 기본 모델은 한 거점을
전량 처리하거나 미처리하며, 부분 처리·거점 재방문은 지원하지 않는다.

## 재현성과 성능

OR-Tools 버전을 고정하고 입력의 대여소·트럭 순서를 정규화한다. 고정 해 개수와
지역 탐색 종료를 사용하며, 기본 계산에는 시계 기반 탐색 제한을 넣지 않는다.
기존 호출과의 호환을 위한 `time_limit_s`를 명시하면 긴급 시간 제한이 적용되지만,
그 모드의 동일 결과는 보장하지 않는다. 이전의 시간 제한 `GUIDED_LOCAL_SEARCH`와
현재의 제한된 지역 탐색은 결과 품질·시간이 다를 수 있으며 최적해를 보장하지 않는다.

```bash
# or-tools/에서 실행. 첫 번째는 200곳 중 예측상 불균형인 곳만 방문 후보다.
../.venv/bin/python -m rebalancing.benchmark --stations 200 --trucks 5 --repeats 3
# 모든 200곳을 방문 후보로 만드는 별도 스트레스 입력
../.venv/bin/python -m rebalancing.benchmark --stations 200 --trucks 5 --repeats 3 --all-candidates
```

출력에는 후보 수, 계산 시간, 버전, 미처리량, 반복 결과의 해시를 남긴다.
측정 범위는 **행렬 준비와 로컬 엔진 호출**이다. Kafka 대기, 실제 OSRM HTTP,
백엔드, LLM을 포함한 "현장 보고부터 변경안 생성까지 10초" 수용 기준은 별도로 검증한다.

이번 변경의 테스트·측정 결과는 [검증 기록](validation.md)에 남겼다.

## 다음 연결 작업

1. [역할 5 명세](../specs/optimizer.md)의 실행 설정 공급·중복 처리 책임을 담당자와 확인한다.
2. 확정 권역의 실제 OSRM 도로망과 캐시에서 200곳·5대 입력을 검증한다.
3. 합의된 요청/응답 스키마로 Kafka 실행기를 붙인다.
4. Vue 공통 뼈대 위에 지도·계획 검토 화면을 만든다.

기존 `docs/or-tools/`의 거리 절감·트럭 수 표는 이전 기본값으로 실행한 역사적 예시다.
현재의 출발 적재량·용량·시간 제약을 적용한 성능 수치로 인용하면 안 된다.

`bikes_moved`와 측정 결과의 `handled_bikes`는 회수·보충 작업 대수의 합이다.
같은 자전거가 회수와 보충에서 각각 집계될 수 있으므로 고유 자전거 수로 해석하지 않는다.
기본 탐색량 50은 빠른 응답을 위한 초기 설정이며 처리량·거리의 최선은 아니다.
평가 때는 탐색량을 바꾼 결과의 미처리 대수·거리·시간을 함께 비교한다.
