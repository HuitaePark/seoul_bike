# OR-Tools로 따릉이 재배치(Rebalancing) 최적화하기

## 1. OR-Tools가 뭐고, 왜 이 프로젝트에 맞나

Google OR-Tools는 **최적화 문제(경로, 배정, 스케줄링, 정수계획 등)를 푸는 오픈소스 솔버 모음**이다.
머신러닝이 "무엇이 일어날지"를 예측한다면, OR-Tools는 "그래서 무엇을 해야 최선인지"를 계산한다.

따릉이의 핵심 운영 문제는 **재배치**다. 출근 시간에는 업무지구 대여소가 가득 차고 주거지 대여소는 텅 빈다.
트럭이 자전거를 옮겨야 하는데, 트럭 수·적재 용량·이동 거리가 모두 제한되어 있어 순서를 사람이 정하면 비효율이 크다.
이것은 OR-Tools의 **VRP(Vehicle Routing Problem) + 적재량 제약**으로 그대로 모델링된다.

## 2. 예제 아키텍처

```
┌────────────────┐   ┌────────────────────┐   ┌────────────────────┐   ┌───────────────┐
│ 1. Data        │   │ 2. Forecast        │   │ 3. Imbalance       │   │ 4. Optimizer  │
│ 대여소 위치/    │──▶│ 시간대별 대여·반납   │──▶│ 대여소별            │──▶│ OR-Tools VRP  │
│ 용량/현재 재고  │   │ 수요 예측 (AI 모델) │   │ 수거(+)/보충(-) 수량│   │ 트럭별 경로    │
└────────────────┘   └────────────────────┘   └────────────────────┘   └───────┬───────┘
 mock_data.py         forecast.py              imbalance.py                     │ planner.py
 (실제: 서울 열린데이터  (실제: 팀의 ML 모델)                                       ▼
  광장 API)                                                              ┌───────────────┐
                                                                         │ 5. Plan       │
                                                                         │ 트럭 경로·수량  │
                                                                         │ (API/대시보드)  │
                                                                         └───────────────┘
```

| 계층 | 파일 | 책임 | 실제 구현 시 교체 대상 |
|---|---|---|---|
| Data | `mock_data.py` | 대여소 30곳, 트럭, 가상 거점 생성 | 서울 열린데이터광장 실시간 대여정보 API |
| Forecast | `forecast.py` | `DemandPredictor` 인터페이스 + 휴리스틱 mock | 팀 AI 모델 (인터페이스만 맞추면 됨) |
| Imbalance | `imbalance.py` | 예측 → "얼마나 빼고/채워야 하는지" 변환 | 그대로 사용 |
| Optimizer | `planner.py` | OR-Tools로 트럭 경로 계산 | 그대로 사용, 제약만 추가 |
| Baseline | `baseline.py` | 최근접 탐욕법(비교 기준) | 평가용으로 유지 |

핵심 설계 포인트는 **예측(AI)과 최적화(OR)를 `Imbalance`라는 좁은 계약으로 분리**한 것이다.
모델을 바꿔도 솔버는 건드릴 필요가 없고, 솔버 없이도 모델을 따로 평가할 수 있다.

## 3. 모델링 (planner.py)

**대여소 상태 → 목표 범위.** 다음 1시간 예측 대여 수 `r`, 반납 수 `t`, 안전 재고 `s`일 때,
1시간 뒤 재고 `bikes - r + t`가 `[s, capacity]` 안에 있어야 대여 불가(빈 대여소)도 반납 불가(만차)도 생기지 않는다.
이를 시작 시점 재고의 건강 범위 `[lo, hi]`로 바꾸고, 범위를 벗어난 만큼이 `delta`다.

- `delta > 0`: 남는 자전거 → **수거(pickup)**
- `delta < 0`: 부족한 자전거 → **보충(dropoff)**

**OR-Tools 모델.**

| 요소 | OR-Tools 표현 | 의미 |
|---|---|---|
| 노드 | `RoutingIndexManager` (0=거점, 나머지=불균형 대여소) | 방문 후보 |
| 비용 | `SetArcCostEvaluatorOfAllVehicles` (하버사인 거리, m) | 이동거리 최소화 |
| 적재량 | `AddDimensionWithVehicleCapacity` ("Load") + 노드별 부호 있는 수요 | 트럭 안 자전거 수가 항상 `0..용량` |
| 선택적 방문 | `AddDisjunction(penalty = 3,000m × 자전거 수)` | 너무 멀면 포기하되 대가를 치름 → 항상 해가 나옴 |
| 트럭 고정비 | `SetFixedCostOfAllVehicles(2,000m)` | 불필요한 트럭 출동 억제 |
| 탐색 | `PATH_CHEAPEST_ARC` → `GUIDED_LOCAL_SEARCH` (5초) | 초기해 후 지역탐색으로 개선 |

적재량 dimension이 핵심이다. 수거는 `+n`, 보충은 `-n`으로 누적되고 `0..용량`을 벗어나면 안 되므로,
**"실어야 내려놓을 수 있다"는 순서 제약이 코드 한 줄 없이 자동으로 풀린다.**

## 4. 실행 결과 (mock, seed=7)

```bash
.venv/bin/python -m rebalancing --hour 8 --trucks 3
```

| 시나리오 | 방식 | 출동 트럭 | 총 거리 | 이동 자전거 | 미처리 |
|---|---|---|---|---|---|
| 08시, 트럭 3대 | 탐욕법 | 2대 | 65.6 km | 54대 | 0 |
| | **OR-Tools** | **1대** | **42.3 km** | 54대 | 0 |
| 18시, 트럭 2대 (보충 수요 > 공급) | 탐욕법 | 2대 | 41.2 km | 28대 | 80 |
| | **OR-Tools** | 2대 | **30.2 km** | **48대** | **60** |

- 08시: **같은 54대를 옮기면서 거리 35% 감소, 트럭 1대 절감.** 탐욕법은 가까운 곳부터 가다가 되돌아오는 낭비가 생긴다.
- 18시: 트럭이 모자란 상황에서 OR-Tools는 **더 짧게 달리고도 더 많이(+71%) 처리**한다. 무엇을 포기할지도 비용으로 판단한다.

> 한 개의 mock 인스턴스 결과이므로 성능 벤치마크가 아니라 **방식의 차이를 보여주는 예시**로 읽어야 한다.

## 5. 이것이 의미하는 것

1. **예측만으로는 운영이 개선되지 않는다.** "내일 8시 강남이 가득 찬다"는 예측은 트럭 경로가 되기 전까지 행동으로 이어지지 않는다.
   OR-Tools는 예측을 **실행 가능한 의사결정(누가, 어디를, 어떤 순서로, 몇 대)** 으로 바꾸는 마지막 단계다. 캡스톤의 AI 모델이 비즈니스 가치로 연결되는 지점이다.
2. **휴리스틱 대비 정량적 근거가 생긴다.** 거리·트럭 수·처리량이 숫자로 나오므로 "AI + 최적화를 쓰면 얼마나 좋아지는가"를 발표에서 증명할 수 있다.
3. **제약이 곧 비즈니스 규칙이다.** 트럭 용량, 거점, 포기 비용은 모두 운영 정책이고 코드의 파라미터다.
   정책을 바꿔 "트럭 1대 늘리면 미처리가 얼마나 줄까"를 시뮬레이션하는 what-if 분석이 가능하다.
4. **예측 정확도의 가치를 측정할 수 있다.** 예측이 틀리면 `Imbalance`가 틀리고 경로도 달라진다.
   모델 오차가 운영 비용에 미치는 영향을 이 파이프라인으로 평가할 수 있다.

## 6. 한계와 다음 단계

| 현재 가정 (mock) | 현실에서 필요한 확장 |
|---|---|
| 직선(하버사인) 거리 | 도로 거리/소요시간 행렬 (카카오·네이버·OSRM) |
| 거점 재고가 충분하고 트럭이 적재 상태로 출발 | 거점 재고 제약, 거점 경유 재적재 |
| 트럭 동일 용량, 1시간 1회 계획 | `vehicle_capacities`로 이종 차량, Time dimension으로 근무시간·시간창 |
| 대여소를 전량 수거/보충 아니면 포기 | 부분 처리(노드 분할) |
| mock 예측기 | 실제 ML 모델 연결, 예측 오차에 대한 안전 재고 튜닝 |
