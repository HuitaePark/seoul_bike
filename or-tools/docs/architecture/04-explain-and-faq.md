# 04. 설명하는 법과 FAQ

이해한 것을 **다른 사람에게 말로 전달**하는 단계다. 먼저 "mock이 뭘 보여준 건지"를 정리하고, 길이별 설명 대본과 예상 질문을 준비했다.

## 1. mock이 보여준 것 / 보여주지 못한 것

```mermaid
flowchart LR
    subgraph REAL["진짜 (실제 로직)"]

        C["제약 검증 테스트"]
    end
    subgraph FAKE["가짜 (mock)"]
        D["대여소 위치·재고"]

    end

```

| 구분 | 내용 |
|---|---|
| **보여준 것 1** | 예측 → 불균형 → 경로까지 **끝까지 연결되어 돌아간다** (구조 검증) |
| **보여준 것 2** | 용량·순서 제약을 **항상 지킨다** (테스트가 여러 seed·시간대로 확인) |
| **보여준 것 3** | 같은 입력에서 OR-Tools가 단순 방식보다 **적은 거리로 같은 일을 할 수 있다** |
| **못 보여준 것 1** | 실제 서울 데이터에서의 절감 효과 |
| **못 보여준 것 2** | 실제 AI 모델을 붙였을 때의 효과 |
| **못 보여준 것 3** | "몇 % 절감"이라는 일반적인 수치 |

한 줄로: **mock의 목적은 성능 증명이 아니라 "이 설계가 끝까지 작동한다"는 증명**이다.

## 2. 길이별 설명 대본

### 10초 (엘리베이터)

> "AI가 자전거 수요를 예측하면, 그 예측을 최적화 도구로 넘겨서 트럭이 어떤 순서로 몇 대를 옮기면 되는지까지 계산하는 시스템입니다."

### 30초

> "따릉이는 시간대마다 어떤 대여소는 비고 어떤 곳은 가득 찹니다. 저희는 먼저 AI로 다음 몇 시간(예: 1시간 단위) 동안의 대여·반납을 예측하고, 그걸 바탕으로 '어디서 몇 대를 빼고 어디에 채울지'를 계산합니다. 그다음 구글 OR-Tools라는 최적화 도구로 트럭이 이동거리를 줄이면서 용량을 지키는 방문 순서를 구합니다. 예측에서 끝나지 않고 실제 작업 계획까지 만드는 것이 핵심입니다."

### 2분 (발표용, 5단 구성)

| 단계 | 말할 내용 | 보여줄 자료 |
|---|---|---|
| ① 문제 | 출근 시간 강남은 만차, 잠실은 빈 대여소. 트럭은 한정 | 01의 문제 그림 |
| ② 구조 | 예측 → 불균형 계산 → 경로 최적화. 계층이 분리되어 교체가 쉽다 | 01의 구성도 |
| ③ OR-Tools | "트럭 용량·거리 같은 조건과 '거리 최소화'라는 목표만 알려주면, 방문 순서는 솔버가 찾는다" | 03의 번역표 |
| ④ 결과 | 같은 54대를 옮기며 탐욕법 65.6km·트럭 2대, OR-Tools 42.3km·트럭 1대 | 02의 비교표 |
| ⑤ 한계와 계획 | "지금은 가상 데이터라 구조 검증용이다. 다음은 실제 API와 AI 모델 연결" | README 로드맵 |

### 시연 순서 (터미널)

```bash
# 1) 전체가 한 번에 돌아가는 모습
.venv/bin/python -m rebalancing --hour 8 --trucks 3

# 2) 시간대를 바꾸면 수요 방향이 반대가 된다 (업무지구 ↔ 주거지)
.venv/bin/python -m rebalancing --hour 18 --trucks 2

# 3) 제약이 지켜지는지 증명
.venv/bin/python -m unittest discover -s tests -t .
```

## 3. 예상 질문과 답

**Q. 그냥 가까운 곳부터 가면 안 되나요?**
A. 그 방식을 `baseline.py`로 직접 구현해서 비교했습니다. 가까운 곳을 먼저 가면 용량 때문에 되돌아오거나 같은 지역을 두 번 지나게 됩니다. 이번 입력에서는 65.6km·트럭 2대 대 42.3km·트럭 1대였습니다. 단, 가짜 데이터 한 건의 결과입니다.

**Q. AI는 어디에 쓰였나요?**
A. 수요 예측 단계입니다. 지금은 mock 예측기이고, 팀 모델을 붙일 자리(`DemandPredictor` 인터페이스)가 준비돼 있습니다. 그 모델이 `predict(station, hour)`만 구현하면 나머지 코드는 수정 없이 동작합니다.

**Q. OR-Tools는 AI인가요?**
A. 아닙니다. 학습 데이터 없이 규칙(제약)과 목표만으로 계획을 계산하는 **최적화 도구**입니다. AI는 "무엇이 일어날지"를 예측하고, OR-Tools는 "그래서 무엇을 할지"를 정합니다. 두 개는 역할이 다릅니다.

**Q. OR-Tools가 구한 게 정말 최고의 답인가요?**
A. 수학적 최적을 보장하지는 않습니다. 제한 시간 안에서 개선을 반복해 찾은 매우 좋은 답입니다. 그래서 "최적해"가 아니라 "비교 방식보다 개선된 경로"라고 표현합니다.

**Q. 예측이 틀리면요?**
A. 안전재고(`safety`)가 완충 역할을 합니다. 예측이 틀리면 불균형 계산이 틀리고 경로도 달라지므로, 예측 오차가 운영 비용에 미치는 영향을 측정하는 것이 다음 과제입니다.

**Q. 실제 서울 데이터에서는 몇 % 줄어드나요?**
A. 아직 모릅니다. 지금 결과는 구조 검증용이며, 실제 데이터로 여러 시간대를 반복 실험해야 말할 수 있습니다. 그 평가 체계를 로드맵 첫 항목으로 두었습니다.

**Q. 왜 이 구조(분리)로 만들었나요?**
A. 예측과 최적화를 `Imbalance`라는 얇은 경계로 나눠서, 한쪽을 바꿔도 다른 쪽이 영향받지 않게 했습니다. 팀원이 서로 기다리지 않고 작업할 수 있습니다.

**Q. 트럭 번호가 0이 아니라 2번인 이유는?**
A. 트럭이 모두 같은 조건이라 어느 트럭이 가도 비용이 같습니다. 솔버가 그중 하나를 골랐을 뿐 의미는 없습니다.

## 4. 자주 하는 오해

| 오해 | 사실 |
|---|---|
| "OR-Tools가 데이터로 학습해서 경로를 배운다" | 학습하지 않는다. 입력된 규칙 안에서 매번 새로 계산한다 |
| "OR-Tools가 항상 최적해를 준다" | 라우팅은 시간 제한 안의 근사해다 |
| "35% 절감이 우리 시스템의 성능이다" | 가짜 데이터 한 건의 결과다. 일반화 금지 |
| "mock이니까 전부 가짜다" | 불균형 계산과 OR-Tools 경로 계산은 실제 로직이다. 입력만 가짜다 |
| "대여소가 비어 있으면 무조건 보충 대상이다" | 곧 반납이 몰려오면 정상이다 (예: 강남-01). 그래서 예측이 필요하다 |
| "OR-Tools가 경로를 코드로 지시한다" | 우리는 문제를 설명할 뿐이고 순서는 솔버가 찾는다 |

## 5. 발전 방향 요약

자세한 내용은 [../ortools-rebalancing.md](../ortools-rebalancing.md) 6장에 있다. 우선순위만 요약하면:

```mermaid
flowchart LR
    R1["① 평가 체계<br/>여러 seed·시간대 반복 실험"] --> R2["② 실제 데이터<br/>서울 API · 도로 거리"]
    R2 --> R3["③ 실제 AI 모델 연결<br/>예측 오차 → 안전재고 튜닝"]
    R3 --> R4["④ 제약 확장<br/>이종 차량 · 시간창 · 거점 재고"]
    R4 --> R5["⑤ 서비스화<br/>API + 지도 대시보드 + 주기적 재계획"]
```

**①을 먼저 하는 이유:** 개선이 실제로 개선인지 판단할 숫자가 있어야 이후 단계의 가치를 증명할 수 있다.

## 6. 스스로 점검하기

- [ ] 벌점(`penalty_per_bike_m`)을 낮추면 결과가 어떻게 바뀔지 예측할 수 있다.
- [ ] "35% 절감"을 왜 일반화하면 안 되는지 말할 수 있다.
- [ ] mock에서 진짜인 부분과 가짜인 부분을 구분할 수 있다.
